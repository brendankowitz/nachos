---
title: Run the worker
---

The worker is the host that turns queued messages into conclusions. With SQL Server it is
`src/Nachos.Worker`, a separate process from the API. With the in-memory provider you do
not run it: the API runs the same loops itself. Read [Memory formation](/nachos/concepts/memory-formation/)
first for what the loops do.

## Prerequisites

- **A database with the M2 schema.** The worker never deploys the schema. The schema
  version number stays `1` before the first release, so a database created by an earlier
  build reads as current but lacks the memory tables. Recreate a pre-release database, or
  review and apply the change once:

  ```powershell
  dotnet run --project src\Nachos.Cli -- schema report --connection "<connection string>"
  dotnet run --project src\Nachos.Cli -- schema upgrade --connection "<connection string>" --approve-reviewed
  ```

  Read [Schema upgrades](/nachos/guides/schema-upgrades/) before touching real data.
- The same connection string the API uses: `Nachos:SqlServer:ConnectionString`, or
  Aspire's `ConnectionStrings:nachos`. The canonical key wins.

## Locally with Aspire and fake AI

```powershell
dotnet run --project src\Nachos.AppHost --launch-profile http
```

The AppHost starts SQL Server, the API and the worker. The worker waits for the API, which
deploys the schema in a Development run. Both hosts get `Nachos__Ai__Mode=Fake`, so no
Azure credentials are needed. The AppHost does not disable authentication; mint a key as
described in the [authentication guide](/nachos/guides/auth/), post a message, then list
conclusions. In a Development run the worker polls for new work at least every two seconds.

## With your own Azure OpenAI

Nachos does not create the Azure OpenAI account and never uses an API key. Create or reuse an
account with a chat deployment and an embedding deployment whose model produces 1536
dimensions (for example `text-embedding-3-small`), then configure **both** the API and the
worker with the same values:

| Setting | Meaning |
| --- | --- |
| `AzureOpenAI:Endpoint` | The account endpoint, for example `https://contoso.openai.azure.com/`. Selects real AI. |
| `AzureOpenAI:ChatDeployment` | The chat deployment name used by profiles that name no model. |
| `AzureOpenAI:EmbeddingDeployment` | The embedding deployment name. |

The API needs them too: it embeds the text of `conclusions/query` and of
API-created conclusions with the same model the worker uses, or the vectors would not be
comparable. Authentication uses `DefaultAzureCredential`: managed identity in Azure, your
`az login` locally. Grant that identity the **Cognitive Services OpenAI User** role on the
account. To run the AppHost against Azure OpenAI, set `AzureOpenAI:Endpoint` (and the
deployments) in the AppHost's user secrets or environment; it then passes them to both hosts
instead of selecting fake AI.

Set `Nachos:Ai:Mode` to `Fake` to force the fake AI even when an endpoint is present.
Outside the Development environment that setting is also the only way to run the fake AI:
a host with no endpoint and no mode refuses to start, so a deployment that lost its Azure
OpenAI settings fails loudly instead of filling its database with fake conclusions.
Per-agent model profiles and fallbacks bind from `Llm`; an agent with no profile of its own
uses `AzureOpenAI:ChatDeployment`. The option table is in [Options](/nachos/reference/options/).

Each embedded conclusion records the model that produced its vector in its internal metadata
(`embedding_model`: the deployment name, or `fake`). Vectors from two models cannot be
compared, and this version does not re-embed existing conclusions, so **switching between the
fake AI and a real model, or between embedding models, needs a new database**.

## In Azure

[`infra/`](https://github.com/brendankowitz/nachos/tree/main/infra) defines a `nachos-worker`
Container App with no ingress, at least one replica, and CPU-based scaling. It reuses the
API's managed identity for SQL and takes your existing Azure OpenAI endpoint through the
`openAiEndpoint`, `openAiChatDeployment` and `openAiEmbeddingDeployment` parameters. Setting
`openAiAccountName` also grants the identity the OpenAI User role on that account (in
`openAiResourceGroupName` if it is in another resource group). These definitions are only
checked offline; deploying them needs the repository owner's approval.

`postdeploy` only checks the API. If `azd deploy worker` fails, the worker keeps running the placeholder image
and nothing says so; check the worker's revision after a deploy.

The replica count stays at one or more. Scaling to zero would need a queue-length scale rule,
which is written but commented out until a run proves it works with the managed identity.

## Operating notes

- `Worker:MaxConcurrency` bounds the units one process handles at once. Replicas are safe:
  a unit is claimed with a lease, and an expired lease is retried by another replica.
- `GET /v3/workspaces/{id}/queue/status` shows pending, in-progress and completed work.
  Work that fails repeatedly is dead-lettered and counts as completed.
- A model or database outage does not dead-letter work. Throttling (429), timeouts (408), server
  errors (5xx) and connection failures from the model, authorization failures from the model
  (401, 403, a token that cannot be acquired, as while a new role assignment propagates), and
  deadlocks, timeouts and failovers of the database are retried with backoff
  (`Worker:RetryDelay` doubling up to `Worker:MaxRetryDelay`) without using one of the unit's
  `Nachos:Deriver:MaxAttempts`. After `Worker:TransientFailuresBeforeError` (10) such failures in
  a row, each further one is logged as an error: check the endpoint, deployments, quota, role
  assignments and the database. Any other failure uses an attempt, and the last attempt
  dead-letters the unit's items. The trade-off: a unit whose own database work always times out
  (for example a very large unit) is retried indefinitely rather than dead-lettered, and shows up
  only as those errors.
- When embedding fails with nothing embedded for `Reconciler:FailedEmbeddingTicksBeforeError`
  (20) reconciler ticks in a row, each further such tick is logged as an error.
- Telemetry: the worker exports traces from the `Nachos.Llm` source and metrics from the
  `Nachos.Worker` and `Nachos.Llm` meters, through the same OpenTelemetry settings as the API.
  The backlog gauges `nachos.queue.eligible_units`, `nachos.queue.oldest_age` (seconds) and
  `nachos.conclusions.embedding_pending` are refreshed once per reconciler tick and reported
  only by the replica that holds the reconciler lease.

## Redrive dead-lettered work

There is no command for this yet. Fix the cause first (a dead letter's `Error` column says
what failed), then return the items to the queue with SQL. Run it against the Nachos
database as a user that can write `dbo.WorkItems`; the worker picks the items up on its next
poll:

```sql
-- Review what is dead-lettered (Status 3), and why.
SELECT Id, WorkUnitKey, Attempts, Error, CompletedAt
FROM dbo.WorkItems
WHERE Status = 3
ORDER BY Id;

-- Make them pending again with a fresh set of attempts. Narrow the WHERE clause
-- (for example by Id or WorkUnitKey) to redrive only some of them.
UPDATE dbo.WorkItems
SET Status = 0, Attempts = 0, AvailableAt = SYSDATETIMEOFFSET(), CompletedAt = NULL, Error = NULL
WHERE Status = 3;
```

Items of one unit are processed in `Id` order, so a redriven item runs before any later
pending item of its unit. The in-memory provider has no equivalent: restart the API to
start over.
