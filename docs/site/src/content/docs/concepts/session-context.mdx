---
title: Session context
---

`GET /v3/workspaces/{id}/sessions/{id}/context` assembles what an agent needs to continue a
conversation: the newest messages, a summary of what came before them and, when asked, what is
known about a peer. Its one hard rule: **the context never exceeds its token budget.**

## Summaries

The worker (or, with the in-memory provider, the API process) keeps two rolling summaries per
session:

- a **short** summary, made every 20 messages (`summary.messages_per_short_summary`): concise,
  factual coverage;
- a **long** summary, made every 60 messages (`summary.messages_per_long_summary`): themes,
  context, preferences.

Each one is cumulative: the model receives the previous summary of its kind and the messages
since it. The cadences, `summary.enabled` and `summary.custom_instructions` can be set per
workspace or session; the deployment defaults and the model budgets are under `Nachos:Summary`
in [Options](/nachos/reference/options/). With the fake AI a summary is just the start of the
newest messages, which only shows the pipeline running.

`GET /v3/workspaces/{id}/sessions/{id}/summaries` returns
`{"id", "short_summary", "long_summary"}`. Each summary is `null` until one has been made, or
`{"content", "message_id", "summary_type", "created_at", "token_count"}`, where `message_id` is
the last message it covers.

## The budget

`tokens` is 1 to 100,000. Without it the budget is 100,000 ("exhaustive within 100,000 tokens"),
and anything outside the range is a `422`. The budget counts **content tokens**, with the same
counter that fills `token_count`: the representation text, each peer-card entry, the summary
content and each message's content. The JSON around them and the field names are not counted.

The context is filled in this order:

1. **Representation and card**, only when `peer_target` is set. Together they get at most half
   of the budget, rounded down. A card larger than that half is left out whole. The
   representation is then cut to the most of its best-ranked conclusions that fit the rest of
   the half.
2. **Summary**, unless `summary=false`. It gets at most 40% of what step 1 left, rounded down.
   The long summary is used when it fits, else the short one, else none: the long one covers
   more of the session for its tokens.
3. **Messages**, newest first, after the point the summary covers (from the start of the session
   when there is no summary). Each message is included whole or not at all, and filling stops at
   the first one that does not fit, so the messages are always an unbroken run ending at the
   newest message. They are returned oldest first. A single message larger than what is left
   gives no messages.
4. **A final check** counts everything again with the same counter. Correct steps never trip it;
   if it ever did, it would log an error and drop the oldest messages, then the summary, the card
   and the representation until the context fits.

The result is `{"id", "messages", "summary", "peer_representation", "peer_card"}`. This rule can
return less than Honcho in overflow cases; it is listed among the intentional deviations in the
[design spec](https://github.com/brendankowitz/nachos/blob/main/docs/superpowers/specs/2026-10-07-nachos-design.md)
(section 9.4).

## Whose view

- `peer_target` adds the representation of that peer and its card. The observer is
  `peer_perspective` when given (it requires `peer_target`), else `peer_target` itself.
- `search_query`, `search_top_k`, `search_max_distance`, `include_most_frequent` and
  `max_conclusions` shape the representation, as on the peer representation route.
  `max_conclusions` and `include_most_frequent` apply with or without `search_query`.
- `limit_to_session=true` narrows the representation to this session; repeated `sessions`
  parameters narrow it to the sessions they name, which must include this one (at most 100).
  Either one hides the card. Narrowing never touches this session's own messages and summary,
  and it can never widen what the caller may see.
- `sessions` cannot be combined with `limit_to_session`, and `scope` is a `422` until scopes
  exist. An invalid combination is a `422` that names the query parameter.

## Keys

A session key, or the key of a peer that is an active member, may read the context and the
summaries of its session. With a peer's key, every session named in `sessions` must also be one
the peer is an active member of, and the observer (`peer_perspective`, else `peer_target`) must
be that peer. A session key may name only its own session in `sessions`, and may pass
`peer_target` or `peer_perspective` only with `limit_to_session=true` or with `sessions` naming
exactly its own session. Otherwise the answer is `401`.
