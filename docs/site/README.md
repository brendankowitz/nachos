# Nachos documentation site

Astro/Starlight source documentation for the current .NET MVP. Builds generate
REST, CLI, options and declaration-compatibility references from this checkout.
They do not establish full SDK conformance, license compliance or release approval.

## Local validation

Use .NET 10 (`global.json`), Node 24 LTS, PowerShell 7 and the exact npm lockfile.
From the root:

```powershell
npm --prefix docs\site ci --ignore-scripts
npm --prefix docs\site run browser:install
$env:DOCS_CONFIGURATION = 'Release'
npm --prefix docs\site run check
npm --prefix .github\scripts ci --ignore-scripts
npm --prefix .github\scripts run check
node --test .github\scripts\docs-artifact.test.mjs
```

Chromium is local to `docs/site/.playwright`. On Linux install its OS dependencies
with `npm --prefix docs/site run browser:install -- --with-deps`.
Run in a clean shell without credentials, SQL/Key Vault configuration or startup
hooks. CI uses `eng/ci/Enter-CiEnvironment.ps1`, private tool homes and disabled
certificate generation/build-server reuse. The reference child separately clears
its environment. No docsite check starts SQL, Docker, Azure or a schema operation.

The whole source-only CI entrypoint is `eng/ci/Invoke-DocsSite.ps1`. It runs
DocsGen in Debug then Release, the serial Node suite, Markdown/artifact tests,
a final Release site build and independent Node/C# provenance verification.
Never build different .NET configurations concurrently in one checkout.

For local browsing use `npm --prefix docs/site run dev` or, after a build,
`npm --prefix docs/site run preview`. Both supported paths prepare references.
Neither publishes anything. The config-command tests cover build/dev/preview.

## Mandatory generated references

`scripts/run.mjs` does this before every supported build:

1. Remove old successful/pending provenance metadata.
2. Build the actual API, CLI and DocsGen, using the same `DOCS_CONFIGURATION`
   (`Debug` by default; explicitly `Release` in CI) for build and execution.
   A missing-assets NETSDK1004 error permits a bounded public-feed restore.
   The runner binds NuGet's import root to the actual restored package cache,
   deletes the old API JSON and its incremental file-list cache, then requires
   the API build to emit a fresh file even when compilation is a no-op.
   A private home must not silently skip OpenAPI build targets.
3. Run DocsGen, then hash all four outputs.
4. Snapshot source inputs **after** generation.
5. Run Astro with a receipt binding those exact generated bytes.
6. Check unchanged inputs, complete output evidence and physical HTML links,
   then finalize provenance.

DocsGen's executable, restore/build intermediates, XML snapshots and private tool
homes live under `artifacts/docsgen`, not the scanned `eng` source tree.
Project references and `dotnet run --project eng/DocsGen` use this layout for
both Debug and Release; product API/CLI/library output locations are unchanged.

Direct Astro builds without the receipt fail. Generation failure cannot bless
stale output. The receipt proves intra-build consistency, not publisher identity
against someone who can replace repository tooling.

Generated files are ignored, never historical cached references:

| File under `src/content/docs/reference/_generated/` | Real input |
| --- | --- |
| `rest-api.json` | Exact `src/Nachos.Api/obj/Nachos.Api.json` bytes |
| `cli.md` | Actual root and recursive command `--help` output only |
| `options.md` | Pure defaults, compiler XML and current API binding facts |
| `compatibility.json` | Exact local wire-manifest vs OpenAPI declarations |

The compatibility file deliberately says `sdkConformance: not-run` and
`authentication: not-assessed`: DocsGen is not a runtime test producer.
Current key/grant routes are implemented declarations, not old 501 snapshots.
Machine-specific binary evidence hashes stay in ignored generated output.
See [DocsGen](../../eng/DocsGen/README.md) for bounded help, input identity and
coherent directory replacement.

The XML-export target retains the recovered, narrowly scoped CS1573/CS0419
nonfatal documentation diagnostics and CS1591 exclusion; it does not relax
normal compilation warnings. Current source exposes 31 such XML warnings.
Nested export builds write ordinary product intermediates: validation is serial,
and concurrent independent builds in the same checkout are unsupported.

## Rendering and ownership boundaries

- Pinned Starlight, Pagefind and local `starlight-openapi`; no downloaded
  upstream schema, sample API or unknown plugin fallback.
- Mermaid renders SVG at build time in Chromium with network requests blocked.
  The browser closes on failure. No client Mermaid renderer ships.
- Astro uses `passthroughImageService()`. The logo exporter uses Chromium.
  Tests reject the unused Sharp/font tooling execution paths.
- Trusted Expressive Code factories and fixed native theme retention are
  constructed internally. Custom factories, EC config and unregistered plugins
  fail instead of borrowing names/ownership from trusted code.
- OpenAPI automatic code examples remain disabled because its native Code
  component cannot serialize the private EC callback. Real operations, schemas,
  responses and navigation remain; examples are not faked.
- The collection link validator is fail-on-error. Dynamic links to injected
  OpenAPI routes use the configured base and are independently checked against
  physical files/anchors, including custom-domain builds.

Existing Astro MDX head-inject/404 priority warnings remain visible.

## Whole-output provenance and local artifact

`dist/.nachos/bundle-modules.json` is the exact sorted package/version union.
`dist/.nachos/output-provenance.v1.json` has the fixed v1 schema:
`schemaVersion`, `build`, `inputs`, `sources`, `outputs`.
The producer records actually observed suppliers conservatively across rendered
pages, not the entire installed dependency graph.

Every physical output, including hidden files, is checked; only the two named
metadata files are excluded from their own output enumeration. Input/package
hashes, lock identities, source usage, output-bound evidence and flat package
union are independently verified. Linked paths, unknown producer kinds,
case aliases and extra/missing/changed files fail.

After the final build:

```powershell
$env:DOCS_SITE ??= 'https://brendankowitz.github.io'
$env:DOCS_BASE ??= '/nachos'
node docs/site/scripts/verify-provenance.mjs
node .github/scripts/docs-artifact.mjs seal . artifacts/ci/docs/tree-seal.json
```

Preserve the same `DOCS_SITE`/`DOCS_BASE` settings as the build: the block
fills in only unset values, using the build's defaults. The custom-domain
integration test builds real output and executes this block.

The artifact helper validates closed USTAR framing, octal fields, padding,
terminators, directory inventory and every regular file's bytes, including
hidden metadata. It rejects links, special files, aliases, GNU/PAX extensions
and tree mutations before/during archiving. It never rebuilds audited output.

## Pages publication

`.github/workflows/docs-site.yml` has independent source and Pages-publication
jobs, with read-only contents permission, pinned setup actions and
credential-free checkout.

The `pages` job runs `Invoke-DocsSite.ps1 -Publication` on PRs and main.
Publication mode installs the locked tools, performs one final site build,
seals the tree, archives the same sealed `dist`, and verifies the archive.

Only `push` or `workflow_dispatch` on `refs/heads/main` uploads
`docs/site/dist` with the SHA-pinned `actions/upload-pages-artifact` action.
The `deploy` job needs both `source` and `pages`, runs only on that same main
condition, has exactly `pages: write` and `id-token: write`, targets the
`github-pages` environment, and contains only the SHA-pinned
`actions/deploy-pages` step. To redeploy without a source change, run the
**Documentation source CI** workflow manually from the `main` branch; PR and
non-main manual runs exercise the provenance/archive checks but do not upload or
deploy.

Before any future release workflow or artifact class is introduced:

- Keep the Pages-only credential/execution profile bounded to
  [#13](https://github.com/brendankowitz/nachos/issues/13); do not add blanket
  workflow-level OIDC or Pages grants.
- Resolve any new emitted-assets and full dependency compliance findings under
  [#19](https://github.com/brendankowitz/nachos/issues/19), including inherited
  Microsoft/distribution findings; a provenance pass is insufficient.
- Independently review the source and final generated artifact.
- Preserve build → seal → verify → archive → verify → upload ordering for Pages,
  with no rebuilding after verification. The separate full-audit job remains
  fail-closed and informational for docs-site publication.
- Azure requires separate consent.
